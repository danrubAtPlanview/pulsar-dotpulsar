# 07 — Performance and zero-allocation design

## 1. Goals

| # | Goal | Measured by |
|---|---|---|
| P1 | **Non-transactional paths do not regress**: send, receive and ack throughput change by ≤ 5%, and allocations per op do not increase. This includes the prerequisite features when they are disabled (the default). | `benchmarks/Transactions` `PlainSend`, `PlainAck` vs baseline commit `e8f2ba2` |
| P2 | **Steady-state transactional send/ack adds 0 B of DotPulsar-owned allocation per op** once the partition or subscription is registered with the transaction. Framework-owned allocations (the task continuation registered by `RegisterOp` when the receipt has not arrived yet) are allowed but must be ≤ 1 object/op and reported. | `TxnSend`, `TxnAck` with `[MemoryDiagnoser]` |
| P3 | **Per-transaction overhead is bounded**: about 10 allocations per transaction (Transaction, 2 dictionaries, Timer, StateManager, TCS, TC op). Nothing scales with the number of messages. | `TxnLifecycle` |
| P4 | Prerequisite features meet their own targets: batching amortizes framing per batch; `ack_set` construction allocates no intermediate arrays. | per feature, see each [06](06-prerequisites/) file |

## 2. Rules (apply everywhere in the new code)

1. **No LINQ, `params` arrays, closures or boxing on per-message paths.** Use `static` lambdas with explicit state
   (`ContinueWith(static (t, s) => ..., state)`), `for` loops, and value-tuple dictionary keys.
2. **Pooled objects are reset field by field, not reallocated.** Proto2 optional fields generated by Google.Protobuf
   have `ClearX()` methods. Use them for `TxnidMostBits`, `TxnidLeastBits`, `RequestId`, `AckSet`, `BatchSize`, and
   the chunk and encryption fields.
   - `SendPackage.Command` (`CommandSend`) and `SendPackage.Metadata` are pooled in `ProducerChannel`.
   - `CommandAck` objects are pooled in `SubConsumer` (`_commandAckPool`).
   - `MessageMetadataObjectPool` returns metadata objects for reuse.

   **Regression tests are mandatory:** send a txn message, then a non-txn message through the same pooled
   objects, and assert that the second carries no txn fields.
3. **Fast-path checks before slow paths.** For example, `Transaction.RegisterProducedTopic`:
   `TryGetValue` + `IsCompletedSuccessfully` → `return default;` (a completed `ValueTask`, no allocation).
4. **`ValueTask` all the way down on hot paths.** Do not convert to `Task` unless the task must be stored or awaited
   twice. `RegisterOp` needs a `Task`, so pass the existing `SendOp.ReceiptTcs.Task` (already allocated by the
   producer) rather than wrapping the `ValueTask`.
5. **`TransactionId` is a 16-byte `readonly struct`**, passed by value (or `in` where the analyzer suggests).
6. **`ack_set` construction:**
   - Compute the bitset words in a `Span<long>`: `stackalloc` when `words <= 16` (batch ≤ 1024 messages), otherwise
     rent from `ArrayPool<long>.Shared`.
   - Then `RepeatedField<long>.Clear()` + `Add` into the pooled `MessageIdData.AckSet`. Google.Protobuf
     `RepeatedField` reuses its backing array after `Clear`.
   - netstandard2.0 has `Span`/`stackalloc` via `System.Memory`, which is already a transitive dependency of
     `System.IO.Pipelines`. Verify; if it is absent, use `ArrayPool` only.
7. **Never block a thread.** Use `SemaphoreSlim.WaitAsync` instead of Java's blocking `Semaphore.acquire`. Timers
   are `System.Threading.Timer` with static callbacks.
8. **Timeout sweeps instead of per-op timers.** The TC handler, ack-timeout tracker, send timeout and chunk expiry
   each use one timer per owner, with a queue ordered by creation time. This mirrors Java (HashedWheelTimer tasks
   per owner).
9. **Batching (WP6)** builds each batch payload in a pooled `IBufferWriter<byte>` (or `SequenceBuilder<byte>` with
   pooled segments) and serializes `SingleMessageMetadata` with `CodedOutputStream` directly into it. One
   `SingleMessageMetadata` instance per container is reused. See [06/producer-batching](06-prerequisites/producer-batching.md).
10. **Encryption (WP9)** encrypts into a rented buffer and reuses `AesGcm` instances per data key (net8+). Details are
    in [06/encryption](06-prerequisites/encryption.md).

## 3. Benchmark project `benchmarks/Transactions`

Copy the structure of `benchmarks/Compression`: a `Transactions.csproj` (net10.0, BenchmarkDotNet, a
`ProjectReference` to `src/DotPulsar`) and a `Program.cs` with `BenchmarkSwitcher`. Add the project to `DotPulsar.sln`
under the `benchmarks` solution folder.

The benchmarks run **in-process against substitutes**, with no broker:

- A hand-written `FakeConnection : IConnection` completes `Send(SendPackage, tcs, ct)` with a `SendReceipt`
  synchronously or via `ThreadPool` (both variants), and `Send(CommandAck ...)` with an `AckResponse`.
- `FakeConnectionPool : IConnectionPool` returns that connection.
- A `PulsarClient` is created with `PulsarClientFactory.CreatePulsarClient(pool, handler, url)`.

Do not use NSubstitute in benchmarks: its proxy allocations would pollute the numbers.

| Benchmark class | Methods | Asserted threshold (documented in the class XML comment and checked manually in the PR) |
|---|---|---|
| `SendBenchmarks` | `PlainSend` (baseline), `TxnSend_SteadyState` (partition pre-registered), `TxnSend_FirstPerPartition` | `TxnSend_SteadyState` allocated bytes − `PlainSend` allocated bytes ≤ size of 1 continuation object (≈ 64-112 B depending on runtime); report the exact number in the PR |
| `AckBenchmarks` | `PlainAck`, `TxnAck_SteadyState`, `TxnAck_BatchIndex` | `TxnAck_SteadyState` − `PlainAck` ≤ AckResponse awaiter + continuation |

### 3.1 Results at the end of WP10 (final tip, in-process, Release, .NET 10)

All thresholds of the table are met except the batching row. The measurements and the comparison with the baseline are in `followups/0007-ack-path-allocations.md` (section "Re-measured on the final tip").

| Row | Threshold | Measured |
|---|---|---|
| `TxnSend_SteadyState` - `PlainSend` | at most 1 continuation (64-112 B) | 0 B (2.88 KB both) |
| `TxnAck_SteadyState` - `PlainAck_Receipt` | at most the awaiter and a continuation | +8 B (+4 B on the thread pool) |
| `CreateCommit_100Sends` vs `Plain_100Sends` | independent of the message count beyond the per-message cost | +1.1 KB for 100 sends |
| `AckSetBenchmarks` | 0 B | 0 B |
| `Send_Batching_1000` vs `Send_NoBatching_1000` | batching at least 3x the throughput | **1.55x** (1.29 us against 2.00 us per message); 3.3x less allocation per message (1.22 KB against 4.09 KB). **Not met** |

**Why the batching row is not met, and what it would take.** Per message, an unbatched send costs `U = X + F`, where `F` is the cost that batching removes (one frame, its serialization and its receipt) and `X` is the cost that stays (the send operation, its task and its receipt, the queue). A batch of 1000 costs `X` plus about `F / 1000` per message. The two measurements give `U` = 2.00 us and a batched cost of 1.29 us, so `X` is about 1.3 us and `F` about 0.7 us (derived from the two numbers and the WP6 note, not from a profile). A ratio of 3 needs `X` of at most about `F / 2`, which is 0.35 us: the per-message part of the send path of the producer would have to become 3.5 times cheaper. That part is the same on master (the plain send is 2.94 KB on master and on the final tip), so meeting the threshold is a performance project for the whole send path of the producer and not a part of the transaction work. Batching does what it is built for here (a frame per batch, a quarter of the allocation per message), but the benchmark can not show 3x with a fake connection, because the fake connection makes a frame cheap.

**Decision (Decided by the requester on 2026-11-01, recorded in `implementation-notes/deviations-summary.md`):** the measured 1.55x throughput and 3.3x less allocation per message are accepted as the criterion of this work, which the XML comment of `BatchingBenchmarks` already states. The threshold of 3x is not reachable without the optimisation of the per-message send path, which would be separate work on code of master; a reviewer who wants the 3x can open it as such.

## 4. Hot-path walkthroughs (what the implementer must achieve)

### 4.1 Transactional send, steady state

```
MessageBuilder.Transaction(txn)              -> stores reference (builder already allocated by user)
Producer.InternalSend
  txn is Transaction t && t.IsOpen            -> field read
  ChoosePartitions                           -> existing
  t.RegisterProducedTopic(topic, ct)         -> TryGetValue + IsCompletedSuccessfully -> default ValueTask  (0 B)
  t.RegisterSendOp(sendOp.ReceiptTcs.Task)   -> Interlocked.Increment; continuation registration        (≤ 1 framework object)
ProducerChannel.Send
  CommandSend.TxnidMostBits/LeastBits = ...  -> pooled command (0 B); cleared in finally
```

### 4.2 Transactional ack, steady state

```
Consumer.Acknowledge(id, txn)
  SubConsumer: t.RegisterAckedTopic(topic, sub) -> value-tuple key lookup (0 B)
  pooled CommandAck: set Txnid*, MessageId[0] mapped (existing pool), RequestId assigned by RRH
  Connection.Send(CommandAck, expectResponse) -> Awaiter TCS (1 object; same cost as any request/response today)
  t.RegisterAckOp(task)                        -> continuation registration
```

Ack receipts inherently need one awaiter per ack, because the broker answers each one. That cost is unavoidable
(Java allocates a `CompletableFuture` too) and is excluded from P2's "DotPulsar-owned" count.
